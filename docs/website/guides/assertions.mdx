## Text and style assertions

<Tabs syncKey="example-language">
  <TabItem label="JavaScript">

    ```js
    await terminal
      .getByText("Ready")
      .getByStyle({ foreground: "green", bold: true })
      .expect();
    await terminal
      .getByText("Settings")
      .getByText("Save", { direction: "after" })
      .unique()
      .expect();
    ```
  </TabItem>
  <TabItem label="Python">

    ```python
    from tui_test import TextStyle

    await terminal.get_by_text("Ready").get_by_style(TextStyle(foreground="green", bold=True)).expect()
    await terminal.get_by_text("Settings").get_by_text("Save", direction="after").unique().expect()
    ```
  </TabItem>
  <TabItem label="Rust">

    ```rust
    use tui_test::{LocatorDirection, TextStyle};

    terminal
        .get_by_text("Ready")
        .get_by_style(TextStyle {
            foreground: Some("green".into()),
            bold: Some(true),
            ..Default::default()
        })
        .expect()?;
    terminal
        .get_by_text("Settings")
        .get_by_text_relative("Save", LocatorDirection::After)
        .unique()
        .expect()?;
    ```
  </TabItem>
  <TabItem label="Go">

    ```go
    if err := terminal.GetByText("Ready", tuitest.TextSelectorOptions{}).GetByStyle(tuitest.TextStyle{Foreground: tuitest.Ptr("green"), Bold: tuitest.Ptr(true)}, tuitest.StyleSelectorOptions{}).Expect(tuitest.LocatorExpectOptions{}); err != nil {
        t.Fatal(err)
    }
    if err := terminal.GetByText("Settings", tuitest.TextSelectorOptions{}).GetByText("Save", tuitest.TextSelectorOptions{Direction: tuitest.After}).Unique().Expect(tuitest.LocatorExpectOptions{}); err != nil {
        t.Fatal(err)
    }
    ```
  </TabItem>
  <TabItem label="CLI">

    ```sh
    tui-test expect text "Ready" --fg green --bold
    tui-test expect text "Save" --after-text "Settings" --match unique
    ```
  </TabItem>
</Tabs>

Text assertions use [locators](/docs/guides/locators/) and retry against the
current screen. Combine text with style or hyperlink constraints when the
visual state matters.

## Negative assertions

<Tabs syncKey="example-language">
  <TabItem label="JavaScript">

    ```js
    await terminal.getByText("Loading").expect({ not: true });
    ```
  </TabItem>
  <TabItem label="Python">

    ```python
    await terminal.get_by_text("Loading").expect(not_=True)
    ```
  </TabItem>
  <TabItem label="Rust">

    ```rust
    use tui_test::LocatorExpectOptions;

    terminal
        .get_by_text("Loading")
        .expect_with(LocatorExpectOptions {
            not: true,
            ..Default::default()
        })?;
    ```
  </TabItem>
  <TabItem label="Go">

    ```go
    if err := terminal.GetByText("Loading", tuitest.TextSelectorOptions{}).Expect(tuitest.LocatorExpectOptions{Not: true}); err != nil {
        t.Fatal(err)
    }
    ```
  </TabItem>
  <TabItem label="CLI">

    ```sh
    tui-test expect text "Loading" --not
    ```
  </TabItem>
</Tabs>

In JavaScript use `expect({ not: true })`; in Python use
`expect(not_=True)`. Negative expectations wait until the locator is absent.

## Command output and exit codes

<Tabs syncKey="example-language">
  <TabItem label="JavaScript">

    ```js
    await terminal.submit("echo complete");
    await terminal.waitCommand();
    await terminal.expectOutput("complete");
    await terminal.expectExitCode(0);
    ```
  </TabItem>
  <TabItem label="Python">

    ```python
    await terminal.submit("echo complete")
    await terminal.wait_command()
    await terminal.expect_output("complete")
    await terminal.expect_exit_code(0)
    ```
  </TabItem>
  <TabItem label="Rust">

    ```rust
    use tui_test::Operation;

    terminal.execute(Operation::Submit {
        data: Some("echo complete".into()),
    })?;
    terminal.execute(Operation::WaitCommand { timeout_ms: None })?;
    terminal.execute(Operation::ExpectOutput {
        text: "complete".into(),
        regex: false,
    })?;
    terminal.execute(Operation::ExpectExitCode {
        code: 0,
        timeout_ms: None,
    })?;
    ```
  </TabItem>
  <TabItem label="Go">

    ```go
    if err := terminal.Submit(tuitest.Ptr("echo complete")); err != nil {
        t.Fatal(err)
    }
    if err := terminal.WaitCommand(tuitest.WaitOptions{}); err != nil {
        t.Fatal(err)
    }
    if err := terminal.ExpectOutput("complete", tuitest.OutputOptions{}); err != nil {
        t.Fatal(err)
    }
    if err := terminal.ExpectExitCode(0, tuitest.WaitOptions{}); err != nil {
        t.Fatal(err)
    }
    ```
  </TabItem>
  <TabItem label="CLI">

    ```sh
    tui-test submit "echo complete"
    tui-test wait command
    tui-test expect output "complete"
    tui-test expect exit-code 0
    ```
  </TabItem>
</Tabs>

`expect output` checks tracked command output and accepts `--regex`.
It is separate from a visible-text assertion. Wait for the command first.
For a directly launched program, wait for process exit before checking its code.

## Window title

`expect title TEXT` accepts `--regex`, `--not`, and `--timeout MS`.
Use it when the application reports state through the terminal title.

## Cursor properties

These property-specific CLI assertions retry. In the high-level bindings, read
the cursor with `getCursor`, `get_cursor`, or `GetCursor` and use your test
runner's assertions.

```sh
tui-test expect cursor --hidden
tui-test expect cursor --visible --shape bar
tui-test expect cursor --x 4 --y 0
```

Only the named properties are checked. Cursor coordinates are terminal cells.
Read `get cursor --json` for position, visibility, shape, and color.

## Terminal modes and colors

These examples use CLI assertion commands. The language bindings expose modes
and colors through session state.

```sh
tui-test expect mode alternate_screen
tui-test expect mode bracketed_paste --off
tui-test expect colors --background '#1d1f21'
tui-test expect colors --foreground 7 --cursor '#ff0000'
tui-test expect colors --palette '1=#00ff00' --palette '200=#123456'
```

Color assertions accept hex RGB, `r,g,b`, or an ANSI palette index.
They check the named slots together; repeat `--palette` for multiple entries.
`default` is not accepted. Use [terminal state](/docs/guides/terminal-state/)
to inspect modes and effective colors.

## Bell counts

`expect bell COUNT` waits until the cumulative bell count reaches `COUNT`.
The language methods are `expectBellCount`, `expect_bell_count`, and
`ExpectBellCount`.

  </TabItem>
  <TabItem label="Go">

  </TabItem>
</Tabs>

Snapshots compare terminal output with an on-disk baseline.
See [snapshot testing](/docs/guides/snapshots/) for baseline creation and updates.

## Assertion timeouts

Locator assertions use the text timeout, five seconds by default.
Override an individual wait with `--timeout MS` or the language's timeout
option. A screen-idle wait is not a substitute for checking the state that
matters to the test.

## Assertion failures

CLI assertion and wait failures exit with code `1`. Language APIs raise or
return typed errors with structured failure details when available.
Configure [failure artifacts](/docs/tools/failure-diagnostics/) or
[traces](/docs/tools/trace-viewer/) before the test to retain screen,
locator, process, and timeline evidence.
